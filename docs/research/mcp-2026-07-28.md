# pi-mcp 对 MCP 2026-07-28 无状态核心与 Tasks 扩展的支持

> 调研日期：2026-11-10。对应 #84（地图 #76 的子票，阻塞 #85）。
>
> 只采用一手来源：
> - MCP 规范：`modelcontextprotocol/modelcontextprotocol@632a0c9a`。它就是 modelcontextprotocol.io 的源文件，`docs/specification/2026-07-28/**` 对应 `https://modelcontextprotocol.io/specification/2026-07-28/**`。我用 versioning 页做过比对，两边正文一致。
> - Tasks 扩展规范：`modelcontextprotocol/ext-tasks@cc9aaac1`，文件 `specification/2026-07-28/tasks.md`
> - 官方博客：`blog/content/posts/2026-07-28-spec-ga/index.md`
> - pi-mcp：本地安装的 `node_modules/.pnpm/@earendil-works+pi-mcp@1.4.0/node_modules/@earendil-works/pi-mcp/dist/`；上游 `earendil-works/pi@a05e3a07` 的 `packages/mcp/`；npm registry
> - 官方 TypeScript SDK：`modelcontextprotocol/typescript-sdk@1e608cae`

>

## 结论

**pi-mcp 1.4.0 不支持 MCP 2026-07-28。** 它只是一个 2025-11-25（legacy）客户端，只额外放宽了 `structuredContent` 这一处，允许任意 JSON 值。它没有实现无状态核心，也没有实现 Tasks 扩展。npm 上最新的 1.5.1（2026-11-09）也一样，上游 main 也还没有做。服务端只支持旧版时，现在一切照常；服务端只支持 2026-07-28 时，现在会连不上。`mcp.ts` 现在只值得做两处小改动（见第 5 节）。真正的升级要等 pi-mcp 支持 2026-07-28（上游 issue earendil-works/pi#10416 仍是 open），或者换成官方 SDK 的 `@modelcontextprotocol/client`。

## 1. 票里的前提有误：`SUPPORTED_PROTOCOL_VERSIONS` 里没有 2026-07-28

`dist/protocol/types.d.ts:3,8`：

```ts
export declare const LATEST_PROTOCOL_VERSION = "2025-11-25";
export declare const SUPPORTED_PROTOCOL_VERSIONS: readonly ["2025-11-25", "2025-06-18", "2025-03-26", "2024-11-05"];
```

上游 main（`packages/mcp/src/protocol/types.ts:4,9`）也是这个值。整个包里提到 2026-07-28 的地方只有两处：

- `dist/client.js:62` 的注释："`structuredContent` may be any JSON value, as MCP 2026-07-28 allows."
- CHANGELOG 1.2.0 的 Breaking Change：`CallToolResult.structuredContent` 从 `Record<string, unknown>` 改成 `unknown`（对应规范 2026-07-28 Minor change 10 / SEP-2106）。

## 2. 无状态核心实现到什么程度：没有实现

下表逐条对照规范 changelog 的 Major changes（`docs/specification/2026-07-28/changelog.mdx`）和 pi-mcp 1.4.0 的实际行为：

| 2026-07-28 要求 | pi-mcp 1.4.0 的实际行为 | 出处 |
|---|---|---|
| 去掉 `initialize` / `notifications/initialized` 握手（SEP-2575） | `connect()` 一律先发 `initialize`，再发 `notifications/initialized` | `client.js:128-145` |
| 每个请求在 `_meta` 里带 `io.modelcontextprotocol/protocolVersion`、`clientCapabilities`、`clientInfo` | `requestInternal` 只往 `_meta` 注入 `progressToken` | `client.js:248-251` |
| 新增 `server/discover` | 没有这个方法 | 全包 grep 无结果 |
| 去掉 `Mcp-Session-Id` 和会话（SEP-2567） | 捕获并回传 `Mcp-Session-Id`；收到 404 时抛 `McpSessionExpiredError`；关闭时发 `DELETE` | `transports/streamable-http.js:258-278, 204-209` |
| 去掉 HTTP GET 流，改用 `subscriptions/listen` | 收到 `initialized` 后会开 GET SSE 流 | `streamable-http.js:177-179, 400-417` |
| 去掉 `Last-Event-ID` 续传 | 仍用 GET 加 `Last-Event-ID` 续传 | `streamable-http.js:310` |
| 去掉 `ping` | 仍处理和发送 `ping` | `client.js:89, 186` |
| MRTR：`resultType: "input_required"` 加 `inputResponses` 重试（SEP-2322） | 不认识 `resultType`。2026 的 `input_required` 结果没有 `content`，会被当成内容为空的成功结果（推断，依据 `validateCallToolResult` 的实现） | `client.js:64-69` |
| `Mcp-Method` / `Mcp-Name` 请求头（SEP-2243） | 不发 | `streamable-http.js:255-262` |
| `structuredContent` 可以是任意 JSON（SEP-2106） | **已支持** | `client.js:62`，CHANGELOG 1.2.0 |

版本协商方面，`connect()` 只接受 `initialize` 返回的版本落在 `SUPPORTED_PROTOCOL_VERSIONS` 里，否则抛错（`client.js:137-139`）。这是 legacy 的协商方式，不能处理 `UnsupportedProtocolVersionError`（`-32022`）。

## 3. Tasks 扩展：不支持

规范要求（`ext-tasks/specification/2026-07-28/tasks.md`）：

- 扩展标识 `io.modelcontextprotocol/tasks`。客户端在每个请求 `_meta` 的 `io.modelcontextprotocol/clientCapabilities.extensions` 里声明它，服务端在 `server/discover` 的 capabilities 里声明它（§Capability Negotiation）。
- 目前只有 `tools/call` 可以返回任务。由**服务端**按请求自行决定是否返回 `CreateTaskResult`（`resultType: "task"`），客户端"do not signal task preference on the request itself"。服务端"MUST NOT return `CreateTaskResult` to a client that did not include the extension capability"。如果服务端只能以任务形式执行，就返回 `-32021` Missing Required Client Capability（§Capability Negotiation、§Supported Methods）。
- 方法：`tasks/get` 轮询，`tasks/update` 提交 `inputResponses`，`tasks/cancel` 协作式取消，不得用 `notifications/cancelled`。旧版的 `tasks/result` 和 `tasks/list` 已删除（changelog Major 6）。
- Streamable HTTP 上发 `tasks/*` 时，必须把 `Mcp-Name` 设为 `taskId`（§Streamable HTTP: Routing Headers）。
- 可选通过 `subscriptions/listen` 接收 `notifications/tasks`，默认用轮询。

**Tool 上的 task 标记：2026-07-28 已删除。** `Tool.execution.taskSupport`（`"forbidden" | "optional" | "required"`）来自 2025-11-25 的实验性核心 Tasks（`schema/2025-11-25/schema.ts:1229-1242`），`schema/2026-07-28/schema.ts` 里已经没有 `ToolExecution`。扩展概览明确写了"No per-tool warmup or per-request flag"（`docs/extensions/tasks/overview.mdx`）。

pi-mcp 1.4.0 的情况：

- `ToolExecution { taskSupport? }` 和 `Tool.execution?` 只有类型声明（`types.d.ts:70-81`），对应的是 2025-11-25 的字段。`listTools()` 原样透传这个字段，`client.js` 里没有任何代码读取它。
- 没有 `tasks/get`、`tasks/update`、`tasks/cancel`、`CreateTaskResult` 或 `resultType` 的处理代码（全包 grep 无结果）。`ClientCapabilities` 里也没有 `tasks` 或 `extensions` 字段（`types.d.ts:19-26`）。
- 结论：2025-11-25 的实验性 Tasks 和 2026-07-28 的 Tasks 扩展都不支持。因为客户端从不声明任务能力，守规范的服务端不会给它返回任务。

## 4. 有没有更新的版本：有，但没有补上 2026-07-28

`npm view @earendil-works/pi-mcp versions` 的结果是 …, 1.4.0 (2026-10-21), **1.5.0** (2026-11-02), **1.5.1** (2026-11-09)。上游 CHANGELOG（`packages/mcp/CHANGELOG.md`）：

- 1.5.0：OAuth 只接受 http(s) URL；HTTP 错误体的摘录不再长期占用内存。
- 1.5.1：新增 `PipeTransport`；新增 OAuth 分段登录 `startMcpSignIn` / `completeMcpSignIn` 和 `createMcpAuthProvider`；新增工具命名和配置辅助 `createMcpToolName`、`normalizeMcpInputSchema`、`limitMcpContent`、`validateMcpServerConfig`；修复了一批 Streamable HTTP / stdio 问题，其中包括 JSON 响应现在受 `maxMessageBytes` 限制，错误体最多读 8 KiB。
- 两个版本都**没有**涉及协议版本、无状态核心或 Tasks。上游 main 的 `SUPPORTED_PROTOCOL_VERSIONS` 仍不含 2026-07-28。

上游跟踪的 issue：earendil-works/pi#10416「Support Stateless MCP (2026-07-28)」，状态 open。提议做成 dual-era：先发 `server/discover` 探测，失败就快速回退。评论里有人提出可以贡献自己的实现，但暂时没有维护者回应。#11353（同主题）被自动关闭（no-action）。

另一个选择是官方 SDK。`@modelcontextprotocol/client` 的 npm latest 是 2.4.0。它的 main（`packages/client/src/client/client.ts:201-230`）提供三种模式：`mode: 'auto'` 先用 `server/discover` 探测，失败就回退到 `initialize`；`{ pin: '2026-07-28' }` 固定用新版；默认 `'legacy'`，行为和 2025 客户端完全一致。Tasks 由独立包 `@modelcontextprotocol/ext-tasks`（0.2.3，peer 依赖 `@modelcontextprotocol/client ^2.2.0`）提供。我没有核实 2.4.0 的发布物是否已包含 `mode`。

## 5. 服务端只支持旧版时怎么协商

规范（`basic/versioning.mdx` §Backward Compatibility、`transports/streamable-http.mdx` 和 `transports/stdio.mdx` 的 §Backward Compatibility）规定，dual-era 客户端按传输方式判断服务端属于哪一代：

- **Streamable HTTP**（Orqestra 只用这种）：先发一个 modern 请求。如果返回 `400`，先**检查响应体**：
  - 响应体里是已知的 modern JSON-RPC 错误（`-32022` UnsupportedProtocolVersion，`data.supported` 列出版本；或 `-32021`、`-32020` HeaderMismatch），说明服务端是 modern，从 `supported` 里选一个版本重试，**不要回退**。
  - 响应体为空，或者不是已知的 modern 错误，说明服务端是 legacy，回退到 `initialize`，之后的请求都按 legacy 版本发送。
  - 官方 SDK 的做法是：HTTP 探测超时算故障，不算 legacy 信号（`client.ts:217-222`）。
- **stdio**：先发 `server/discover`。返回 `DiscoverResult` 或已知 modern 错误，说明是 modern。返回其他任何错误或超时，说明是 legacy，回退到 `initialize`。回退"MUST NOT be keyed to one specific error code"。
- 判断结果属于服务端，而不是单个请求。客户端应按 origin（HTTP）缓存这个结果，也可以跨重启持久化；如果之后发现判断有误，再重新探测。

pi-mcp 1.4.0 现在的表现（推断，依据上面的源码）：

- legacy 服务端：正常工作。
- dual-era 服务端：收到 `initialize` 时走 legacy 语义，正常工作。
- **只支持 modern 的服务端**：我们的 `initialize` 缺少必需的请求头和 `_meta`，服务端按 §Server Validation 返回 `400`，`checkResponse` 抛出 `McpHttpError(400)`。这时 Run 会跳过该服务器，只记一条日志（`mcp.ts:79-82`）；控制台的连接测试返回 `reason: "failed"`，`detail` 只是一句笼统的 HTTP 错误，用户看不出原因是"服务端只支持 2026-07-28"。

## 6. `mcp.ts` 需要改什么

**现在就能做，不依赖 pi-mcp 升级：**

1. **测试结果给出可读原因**：在 `testMcpServer` 的分类（`mcp.ts:147-157`）里，如果 `error instanceof McpHttpError && error.status === 400`，并且 `error.body` 能解析成 `code: -32022` 的 JSON-RPC 错误，就给 `detail` 写明"该服务器只支持 MCP {data.supported}；当前客户端只支持到 2025-11-25"。这一条在服务端只支持 modern 时有用。`McpHttpError.body` 已存在（`streamable-http.js:85-92`）。是否新增一个 `reason` 值，由 #76 决定。
2. **（可选）升级到 1.5.1**：它修复了 JSON 响应不受大小限制、错误体会被整体读入等 HTTP 问题。我们用到的 API（`McpClient`、`StreamableHttpTransport`、`toLlmContent`、`McpHttpError`、`McpTimeoutError`）在 CHANGELOG 里没有 breaking 记录。它的 `createMcpToolName` 和 `normalizeMcpInputSchema` 可以替换 `mcp.ts:49-59` 里手写的命名和 schema 处理逻辑，但命名规则不同（`mcp__<server>__<tool>` 加哈希后缀），会改变已有 Tool 的名字，所以不建议顺手替换。

**不需要改的：**

- `execution.taskSupport`：我们不声明任务能力，2025-11-25 服务端不会返回任务。2026-07-28 也已经删掉了这个字段，以后不会再用它来判断，所以不必为它写过滤逻辑。如果某个 2025-11-25 服务端的工具标了 `required`，非任务调用会失败，错误会作为调用失败交给模型（推断）。
- `isError` 的处理（`mcp.ts:72-73`）符合 2026-07-28 的 Tool Execution Errors 规则（`server/tools.mdx` §Error Handling），不用改。

**等客户端支持 2026-07-28 之后才需要改的（交给 #85 和后续实现票）：**

- `connectMcpServer` 改成 dual-era 连接，并按 origin 缓存服务端的代次（可以存在 `McpServer` 配置上）。
- `execute` 要处理三种 `resultType`：`complete`、`input_required`（MRTR，需要工具审批或 elicitation 的界面），以及声明 Tasks 扩展之后的 `task`。`task` 结果的轮询、取消和持久化 `taskId` 怎么映射到 Run、Inbox、Timer，是 #85 的问题。
- 2026-07-28 的 `tools/list` 结果带 `ttlMs` / `cacheScope`，可以用来缓存工具列表（Minor 5），这一项是可选的。

## 7. 升级路径

1. **现在**：继续用 pi-mcp，可以升到 1.5.1。按第 6 节第 1 条改进测试结果的提示。这样 legacy 和 dual-era 服务端都能用，只支持 modern 的服务端会给出明确提示，不再是笼统的失败。
2. **pi-mcp 支持 2026-07-28 时**（关注 earendil-works/pi#10416，以 `SUPPORTED_PROTOCOL_VERSIONS` 包含 `"2026-07-28"` 为准）：升级，并按第 6 节"等客户端支持之后"的清单接入。Tasks 是否由 pi-mcp 支持，还是要我们自己通过 `client.request("tasks/get", …)` 实现，到时再看。pi-mcp 的通用 `request()` 已经能发任意方法（`client.js:154`），但还缺 `_meta` 能力声明和 `Mcp-Name` 请求头。
3. **如果迟迟没有进展，或者 #85 需要 Tasks 时**：把 `mcp.ts` 换成官方 `@modelcontextprotocol/client`（`mode: 'auto'`）加 `@modelcontextprotocol/ext-tasks`。`mcp.ts` 只有约 170 行，替换面不大，但测试用的是 pi-mcp 的 transport 注入，需要一起改。换之前要先核实已发布版本里确实有 `mode`。不建议自己 fork pi-mcp 来补协议。
