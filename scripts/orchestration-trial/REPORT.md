# Subagent 编排稳定性实测：#180 之前的基线

2026-11-19，在 verify-orqestra 实例上用真实 Model 跑了 15 个顶层 Conversation。目的是在做 #180（Agent Definition 声明能派哪些 Subagent 模板）、按任务选 Model 或输出 schema 之前，先知道今天的编排坏在哪里。原始数据在 `results/20261119-0527/`，完整统计表在其中的 `metrics.md`。

## 结论

- **派错模板一次都没有发生。** 负责人直接派出的 30 个子任务全部落在对口的团队模板上，嵌套派出的 66 个也没有一个落在干扰模板上。无此模板和预算两类拒绝都是 0。按这组数据，#180 要挡的那类失败在这个场景里测不出来。
- **负责人第一次调用 `subagent` 工具，10 次有 10 次因参数形状不对被拒。** 它把 `{template, brief}` 平铺在顶层并行调用三次，工具要的是 `tasks: [...]`。重试一次就对了。153 次 subagent 调用里被拒 57 次，只产出被拒调用的步骤占总成本的 14%。
- **没有 Sandbox 时，团队成员会为了"交文件"再派子任务。** 30 个直派子任务全部又派了下级，66 个二级子任务里 65 个的任务说明是写入或核对 `/workspace` 下的文件。负责人给成员的 30 份说明也全部要求写 `/workspace` 文件。原因是 `subagent` 工具的描述无论有没有 Sandbox 都说"你们共享 sandbox，把文件留在 /workspace/subagents/"。二级子任务花掉 31% 的成本。
- **子任务的成果会在交付时丢掉。** Notification 只带子任务最后一次 Run 的答复。30 个直派子任务全部被自己的下级唤醒过至少一次，其中 7 个整棵子树写了 4000 多个 output token，送到负责人手里却不到 3000 字，常见的是"报告已写入 /workspace/…"，而那个文件并不存在。
- **负责人的汇总不可靠。** 在 10 次有委派的运行里，评判发现最终答复丢了已送达的实质发现 8 次，把子任务没说过的话安到它名下 7 次，结果送达前就提前声称 2 次。
- **能跑完。** 14 次空闲结束，1 次以向用户提问结束，0 次失败或卡死。可委派可不委派的任务 5 次都没有委派，中位 17 秒、0.0034 美元答完。

据此的建议：先修工具描述里的 Sandbox 假设和 `subagent` 的参数形状，再用这套脚本重跑。#180 如果要做，理由应是管理上的可控性，而不是稳定性。输出 schema 是三项里唯一对准已测到的失败的一项。

## 设置

- **实例**：`.claude/skills/verify-orqestra` 起的隔离实例，用自己的 Postgres（55432）和 RustFS。没有 Search Provider、Sandbox Provider、Document Parser，也没有 MCP Server。Limits 是默认值，Subagent 最大深度 2，每棵树同时最多 4 个 Subagent，每条用户消息最多 16 次启动。
- **Model**：从开发库读出 `deepseek` Provider 的 key，在内存里解密后经 api 配进实例。所有 Run 都在 `deepseek/deepseek-flash` 上，thinking 为 `low`，即 composer 的默认值。Subagent 按 ADR 0012 跟随父 Conversation 的 Model。
- **Agent Definition**（`fixtures.ts`）：
  - 可选的负责人 `tech-lead`。它的指令写明团队成员是"安全评审、性能评审、技术文档工程师"，写的是名称，不是 id，并要求收齐结果后整合。
  - 3 个不可选的团队模板：`security-reviewer`、`perf-reviewer`、`tech-writer`。
  - 5 个不可选的干扰模板：中英翻译、营销文案、合同审阅、招聘助理、客服话术。
  - 实例自带的可选 Agent `general`。
  - 所有 Definition 的 `tools` 都是 `[]`。
- **任务**：用户口吻的中文提问，3 个任务各跑 5 次，按任务轮流发送。
  - `review`：给一段有注入、N+1、无文档问题的 Express 代码，要求从安全、性能、文档三方面评审并汇总排序。
  - `writeup`：为"批量导入用户"接口准备安全清单、压测方案和前端接口说明，再整理到一起。
  - `optional`：一个 ReDoS 正则问题，可以派人，也可以直接答。
- **发送方式**：每次一个新的 Incognito Conversation，这样 Memory 和 Recall 不会把一次运行的内容带进另一次。消息走网页用的同一个 `POST /api/messages`。脚本轮询数据库，直到整棵树没有 Run 在跑、Inbox 里没有会唤醒的输入、没有排队或运行中的 Subagent，并连续两次如此。每次最多等 10 分钟。
- **度量**：全部从数据库读取。`conversation`、`subagent`、`message`（含每条 Notification 的原文和每条 assistant 消息的 usage）和 `usage` 表。
- **评判**：5 个 Opus（effort high）评判，每个只看一份材料。一份材料包含每个任务各一次运行，标签打乱，看不到 Model 名和 Conversation id。材料里有负责人的每条消息，以及每次送达给负责人的原文。细则在 `judge-rubric.md`，共五项：提前声称、遗漏、捏造或错归属、覆盖度、备注。
- **花费**：`usage` 表合计 1.94 美元，共 16 个 Conversation，即 15 次正式运行加 1 次试跑。15 次正式运行是 1.93 美元。评判的花费不在其中。

跑之前定的判据是：派错模板（干扰模板、负责人自己、无此模板）在 15 次里出现 2 次以上，才算 #180 有可测的稳定性收益。

## 失败样例

1. **参数形状不对**（review-1，`2375faea-b426-4387-97f6-ef57fdde1f79`）。负责人第一步并行发出三次调用，每次形如 `{"template": "security-reviewer", "brief": "…"}`，都被拒为 `tasks: must have required properties tasks`。10 秒后它改成一次带 `tasks` 数组的调用。三份被拒的说明都包含整段代码，这些 output token 白花了。其余 9 次有委派的运行，第一步都是同一个形状。
2. **为交文件再派下级**（同一次运行）。文档工程师派了一个 general 子任务去"检查当前沙箱的写入能力"。安全评审派了一个文档工程师子任务"把报告逐字原样写入 /workspace/subagents/security-report.md"，之后又派了三个 general 子任务核对这个文件。性能评审交回"评审完成。报告已写入 `/workspace/subagents/perf-report.md`"，这句话不成立。负责人在最终答复里指出了这一点。
3. **成果没送到负责人**（review-2，`636a6589-8708-4a5a-830a-0d76643fa3a9`）。安全评审把定稿的 18 条评审写进了给下级"记录员"的任务说明里，自己那一轮只回了一句"记录员正在写入"。下级回报后它被唤醒，最后一轮写的是"必须更正我前面的说法：报告文件没有写成"。负责人收到的唯一一条 Notification 就是这段 1206 字的更正，18 条评审本身没有送到。
4. **缩水之后补写**（writeup-3，`c69a76f7-93a3-45b4-b545-4c6e8a73ea5c`）。安全评审只送达 825 字："清单在 `/workspace/security-checklist.md`（98 行，P0 24 条 / P1 14 条 / 可接受 7 条）"，加上 3 条风险和一串编号。负责人的最终答复列出了具体的 P1 项、可接受风险和一条路径穿越，并写在安全评审名下。这些内容安全评审都没有送达。
5. **错归属**（writeup-2，`8569ae01-5d70-432b-9d47-20b15efc5d28`）。最终答复的第 5 道闸门写"全链路禁止 upsert（无 `ON DUPLICATE KEY UPDATE`）"，来源标为"安全 AUTH-05 / 性能"。性能评审的原文是"用 `ON DUPLICATE KEY UPDATE col=col`，靠 `affected_rows` 区分新增和未变"。两个评判各自独立标出了这条，也对照过原文。
6. **提前声称**（review-2）。t+139s 时只送达了文档评审，负责人写"从性能和安全的意见看，我倾向于异步方案"。性能评审 t+217s 才到，安全评审 t+403s 才到。
7. **以提问结束**（review-4，`1bca4b9c-3f05-4005-b2c6-94f11e97ee88`）。t+182s 安全评审送达后，负责人调用 `ask_user`，问"`/orders/search` 到底是谁在用？"，并给了四个建议答案。按设计，性能和文档的 Notification 会在 Inbox 里等用户回答。用户看到的是一个问题，而不是汇总。脚本最初把它记成卡死，现已改为 `question` 状态。
8. **原始工具标记**。7 次运行里有 30 条 assistant 消息把 DeepSeek 的原始工具调用标记（`<｜｜DSML｜｜ calls>`）当成正文输出。这些是没有工具的子任务在"执行"shell 命令。其中 18 条作为 Notification 送到了一级子任务，没有一条送到负责人。

## 每个数字受什么限制

- **只有一个 Model。** 所有 Run 都在 deepseek-flash、thinking low 上，负责人和成员都是。10/10 的参数错和那些原始工具标记，可能是这个 Model 的习惯：它倾向于并行发多次调用，而不是在一次调用里传数组。换 Model 后是多少没有测。
- **没有 Sandbox。** 二级派遣、文件核对、交付缩水都和"工具描述承诺了 Sandbox，实际没有"有关。有 Sandbox 的部署里，`/workspace` 交接按设计能用，这几项的数字会不同，没有测。所以这里的数字描述的是没配 Sandbox 的部署，verify 实例默认就是这样。
- **派错为 0 是一个容易的场景。** 负责人的指令写出了三个角色名，干扰模板与任务明显无关，也没有"代码评审"这类相近的模板。指令不写角色名或有相近模板时的派错率没有测。样本量方面，10 次有委派的运行里 0 次派错，按 95% 置信，每次运行的派错率上限约 26%。按 96 次启动算上限约 3%，但同一次运行里的启动并不独立。
- **评判类数字用"有没有"，不用"多少条"。** 第 1、2 份材料（6 次运行）由另一组评判独立再判了一次，见 `judge-recheck.json`，那次的材料格式略旧。两次在提前声称、有无遗漏、有无捏造、覆盖度四项上 6/6 一致。条数差别大，例如 R06 的遗漏是 6 条对 3 条，R08 的捏造是 3 条对 1 条。另外 5 份材料由 5 个评判分别判，宽严可能不同。第 5 份材料的评判明显更宽，R12 判为没有问题。review-4 在负责人提问时结束，它的 9 条遗漏主要来自提前结束，不是汇总丢的。
- **"交付缩水"是一个粗的启发式。** output token 包含推理 token。7 个里有 1 个（writeup-1 的安全评审，4231 token，送达 2180 字，写着"以下为完整正文"）可能只是一份短但完整的清单。
- **Outcome 不反映交付质量。** 96 个子任务里 95 个是 completed，包括只交回指针和只交回更正的那些。Outcome 只说 Run 怎么结束，不说交了什么。
- **墙钟受串行链条限制。** 一次有委派的运行要走完负责人、成员、二级、成员重跑、负责人这条链。成员首次答完后平均还要再等 85 秒（中位）才送达。生成本身也慢，review-1 一次输出了 117k token。每棵树同时最多 4 个 Subagent，试跑时看到过一次排队，没有计数。
- **工作确实发生了。** 每次空闲结束的运行都有最终答复，usage 也大于 0，`collect` 里有断言。Model 请求错误是 0 次。第一次试跑因为 shell 的 `HTTPS_PROXY` 连不上 DeepSeek 而失败（`Connection error.`），去掉代理重起实例后才开始正式数据，那次试跑不计入。
- **成本按 Catalog 价格计**，来自 `usage` 表，不含评判。

## #180、按任务选 Model、输出 schema 各能解决什么

| 测到的失败 | 次数 | #180 | 按任务选 Model | 输出 schema | 直接对准它的改法（推断） |
|---|---|---|---|---|---|
| 派给干扰模板、自身或不存在的模板 | 0/96 | 能，直接挡住 | 不能 | 不能 | 无需改 |
| `subagent` 参数形状被拒 | 负责人 10/10 次运行，占成本 14% | 不能 | 不能。负责人跑在用户选的 Model 上，按任务选只影响 Subagent | 不能，它管输出不管输入 | 让工具接受单个 `{brief, template}`，或在描述里给一个数组示例 |
| 无 Sandbox 时为交文件再派下级 | 30/30 直派，65/66 二级 | 基本不能。按 #180 的写法，不带模板的 general worker 始终可用，成员仍能派它 | 不能 | 不能 | 工具描述只在有 Sandbox 时提 `/workspace`；Limits 里的最大深度设为 1 现在就能关掉嵌套 |
| 成果没送到负责人（交付缩水） | 7/30 | 不能 | 不能 | 部分能。要求结果带发现列表的话，只有更正或指针的答复会被拒 | 让被唤醒的子任务知道最后一条答复会替换它的结果 |
| 汇总遗漏已送达的发现 | 8/10 | 不能 | 没测，换负责人的 Model 才可能有影响 | 部分能。发现有编号，平台才能机械核对哪条没进最终答复 | 平台侧核对 |
| 错归属、捏造 | 7/10 | 不能 | 没测 | 部分能，理由同上 | |
| 结果送达前提前声称 | 2/10 | 不能 | 不能 | 不能 | |
| 以提问结束 | 1/15 | 不能 | 不能 | 不能 | 可接受，按 ADR 0001 的设计 |

结论是，#180 对准的失败在这里是 0 次。按 #180 现在的写法，它也挡不住测到的最大一类开销，即成员为了交文件再派下级。按任务选 Model 改变不了负责人，测到的问题也不在 Subagent 的能力上。输出 schema 对准了交付缩水和汇总核对，但只有平台真的去核对，汇总遗漏才会少。

## 复跑

```bash
bun scripts/orchestration-trial/trial.ts
```

步骤和评判方法见 `README.md`。建议的顺序是：先改工具描述和参数形状，重跑；再做输出 schema，重跑；需要时再做 #180，在 `fixtures.ts` 里给负责人加上名单，重跑。三次都和这份基线对照。
